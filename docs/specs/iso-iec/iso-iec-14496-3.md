# ISO/IEC 14496-3: description from free sources

A description of the parts of ISO/IEC 14496-3 (*Coding of audio-visual objects — Part 3: Audio*, 2019) that the deliverables need, written for this project from free sources ([README](README.md)). It is not the standard.

## 1. Scope

AudioSpecificConfig (ASC) identifies an MPEG-4 audio object and supplies its sampling and channel configuration. AAC can carry it in Matroska codec private data, the MP4 `DecoderSpecificInfo`, or the AAC sequence header in FLV. For an applicable AVI format, inspect the AAC payload type and use the configuration bytes defined for it. LATM multiplexes audio. LOAS can add synchronization around that multiplex. An RTP mapping can convey the multiplex configuration separately. [Matroska codec mappings](https://www.ietf.org/archive/id/draft-ietf-cellar-codec-21.html) · [Microsoft HEAACWAVEINFO](https://learn.microsoft.com/en-us/windows/win32/api/mmreg/ns-mmreg-heaacwaveinfo) · [RFC 6416](https://www.rfc-editor.org/rfc/rfc6416)

## 2. AudioSpecificConfig

Sources: `multimedia-wiki-mpeg-4-audio` and `yohhoy-isobmff-notes`, both community sources. Fields are read most-significant bit first, without byte alignment.

| Field | Bits | Meaning |
|---|---|---|
| `audioObjectType` | 5 | The object type; 31 is an escape, after which 6 more bits give the type minus 32 |
| `samplingFrequencyIndex` | 4 | An index into the table of section 3; 15 is an escape |
| `samplingFrequency` | 24 | Only when the index is 15: the rate in hertz |
| `channelConfiguration` | 4 | Section 4. A zero sends the reader to object-specific configuration, such as a program configuration element for general AAC |

For AAC object types 1 through 4, the object-specific data begins with a general audio configuration. For hierarchical SBR (type 5) or PS (type 29), read the common core sampling frequency and channel configuration first. Next read the extension frequency index (and its explicit frequency if escaped), then the underlying audio object type. The two rates describe different stages. RFC 6416 illustrates a 24000 Hz AAC core with 48000 Hz SBR output. Its PS example also shows why the core channel configuration alone cannot establish the output channel count. [RFC 6416, sections 7.4.1.5–7.4.1.7](https://www.rfc-editor.org/rfc/rfc6416#section-7.4.1.5)

In backward-compatible explicit signaling, an 11-bit extension identifier `0x2B7` can occur after the object-specific configuration. For extension object type 5, a presence bit signals SBR and, when set, an indexed or explicit extension frequency follows. A subsequent identifier `0x548` can carry the PS presence bit. Only examine these fields at a known syntactic boundary with enough bits remaining. [ISO/IEC 14496-3:2009/Amd.1, table 1.15](https://cdn.standards.iteh.ai/samples/53944/df43eb467f3f4c9e935c26babad9de3d/ISO-IEC-14496-3-2009-Amd-1-2009.pdf)

The named object types in scope are 1 AAC Main, 2 AAC LC, 3 AAC SSR, 4 AAC LTP, 5 SBR and 29 PS. Other recognized numerical values can be retained without assigning a profile name (`multimedia-wiki-mpeg-4-audio`, `rfc6416`).

| 0 | 96000 | 7 | 22050 |

## 4. Channel configuration

For the common AAC configurations, 1 is front center and 2 is front left/right. Configuration 3 adds front center to the stereo pair. Configuration 4 adds a back center to those three. Configuration 5 has the three front channels and a rear pair, and 6 adds LFE to that layout. Configuration 7 denotes eight channels: three front, two side, two rear and LFE. The remaining codes need an object- and edition-specific mapping before assigning a layout. Source: `multimedia-wiki-mpeg-4-audio`.

## Gaps

- Backward-compatible explicit signaling puts an extension after the object-specific configuration. Implicit signaling can leave it out of the ASC altogether. The cited amendment describes the trailing fields. Locating them still requires parsing the preceding object-specific configuration. An absent or unexamined extension leaves the output parameters unresolved. [ETSI TS 102 005, annex A.4.1.2](https://www.etsi.org/deliver/etsi_ts/102000_102099/102005/01.04.01_60/ts_102005v010401p.pdf) · [RFC 6416, section 7.4.1](https://www.rfc-editor.org/rfc/rfc6416#section-7.4.1)
- A full general audio configuration, including a program configuration element for channel code zero, remains outside the supported header fields. When its end cannot be determined, leave the extension unread.
- RFC 6416 supplies LATM examples and RTP carriage rules. It does not supply a complete LOAS sync-layer parser or all `StreamMuxConfig` and `AudioMuxElement` branches for the Phase 10 transports.
